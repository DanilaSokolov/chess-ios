## Архитектура: разделение на сервисы

Сейчас всё работает в одном процессе `server`. Как в больших онлайн-играх, разделяем по логическим
частям: у каждой своя ответственность, своя БД и свой темп релизов. Игровой сервер не должен зависеть
от доступности остальных во время партии.

```
                 gRPC                               WebSocket (+ access token в Hello)
iPhone/Mac ──────────────► auth ──── JWT ──► клиент ─────────────────────► game (gateway + комнаты)
                            │ Postgres(users)                                  │  проверяет JWT сам,
                            │ GetPublicKeys (gRPC) ◄── game забирает и кэширует ┘  по публичному ключу
                                                                               │
                                                     события партий (Kafka/NATS, outbox)
                                                                               ▼
                                                     profile/history ── Postgres(games, stats)
                                                          ▲ HTTPS: история, профиль, рейтинг
                                                          └──────────────── клиент
```

- [x] **auth**: отдельный сервис идентификации (cmd/auth, gRPC, свой Postgres)
  - Вход: Sign in with Apple, логин+пароль (argon2id), анонимный вход. Анонимные id тоже выдаёт auth,
    сейчас это делает game
  - Выдаёт короткий access token (JWT, 15 мин, подпись Ed25519) и долгий refresh token (ротация, отзыв)
  - [x] Отдаёт открытые ключи (`GetPublicKeys`). Game проверяет токен локально и не ходит в auth на каждое подключение,
    поэтому падение auth не рвёт идущие партии
  - Свой Postgres: `users`, `identities` (apple sub, login), `refresh_tokens`
  - Rate limit на вход, защита от перебора паролей
- [ ] **game**: то, что есть сейчас (gateway, matchmaker, комнаты)
  - `Hello.access_token` вместо имени. `sub` из токена — постоянный `user_id`, имя берётся из claims
  - Без состояния аккаунтов. Пишет только события партий (`GameStarted`, `GameFinished`) через outbox
  - Горизонтальное масштабирование: matchmaker выносится в отдельный сервис (очередь в Redis),
    комнаты распределяются по нодам, клиент получает адрес ноды с партией
- [ ] **profile/history**: читает события партий, хранит историю, статистику и рейтинг, отдаёт API клиенту
- [ ] Общий контракт: `proto/` для событий между сервисами, версии событий как в btc-indexer

## iPhone Duo (складной iPhone)

Внешний экран 5,4″ ведёт себя как обычный iPhone. Внутренний 7,6″ почти квадратный, по ширине как
iPad (regular × regular) и **не учитывает** поддерживаемые ориентации. Раскладку выбираем по size class
и геометрии, а не по модели устройства: `UIScreen.main` и `userInterfaceIdiom` в коде нет, так и оставляем.
См. [Prepare your app for iPhone Duo](https://developer.apple.com/videos/play/tech-talks/111461/).
API iOS 27.1 сверены по SDK Xcode 27.1: `onHingeChange` / `DeviceHinge` (closed / partiallyOpen / fullyOpen + угол),
`GeometryProxy.reservedRegions(kind: .division | .occlusion)`. В macOS SDK 27.0 их нет — код под `#if os(iOS)`.

- [x] **Экран партии без пересоздания доски.** `GameLayout` (свой `Layout`): дочерние view всегда одни и те же,
  раскладку и все кадры считает `GameScreenGeometry.plan` (чистая арифметика, тесты `GameScreenGeometryTests`)
- [x] Гистерезис «столбиком» ↔ «рядом»: ±5% (`switchMargin`) от текущей раскладки, окно Mac у порога не мерцает
- [x] Раскладка решается по измеренным высотам строк (`onGeometryChange`), `Chrome.estimate` — только до первого замера
- [x] «Столбиком» при нехватке высоты: доска не меньше 200 pt (`minBoard`), детали получают остаток и прокручиваются,
  на строку игрока не наезжают
- [x] Одна пропорция доски: `GameLayout` получает `boardAspect` от `GameView`, а не спрашивает у доски; кэш высот в `Layout`
- [x] **Чат колонкой рядом с доской** (как Telegram на iPad), если по высоте остаётся ≥ 200 pt, иначе кнопка и шторка
- [x] **Поза «домиком» (tabletop)**: полураскрыт, сгиб поперёк → доска и строка игрока снизу, соперник/статус/ходы/чат сверху,
  в сгиб ничего не ставится. Поза «книжкой» (сгиб вдоль) → «рядом», граница колонки — сгиб, доска в большей половине.
